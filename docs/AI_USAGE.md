# AI 对话记录：排行榜功能调研

本文档记录了为 HTML5 塔防游戏添加排行榜功能、防止重放攻击和刷榜的调研过程。

---

## 1. 客户端验证的可行性

prompt:

通过在波次的开始和结束时，对允许产生的最大积分和金币进行核对，从而避免结果伪造，请问这个想法是否务实？

answer:

客户端验证存在根本局限性。验证代码和游戏逻辑都运行在用户浏览器中，用户拥有完全的代码控制权，任何客户端检查都可以被绕过。

核心问题：
- 验证函数本身可以被替换为空函数
- 验证阈值可以被修改为无限大
- 全局变量（TD.money, TD.score）可以直接修改

结论：对于单机休闲游戏，轻量级客户端检查可以防止意外溢出和低技术门槛作弊；但如果有排行榜功能，必须走服务端验证路线。

---

## 2. 服务端验证的内容和思路

prompt:

是的，如果要加入排行榜功能，在服务端加入校验，从而避免积分和金币结果伪造。请给出需要校验的内容和思路。

answer:

服务端验证采用四层验证架构：

**Level 1: 格式验证**
- 会话有效性
- 数据完整性
- 时间戳合理性
- 操作日志时序

**Level 2: 规则验证**
- 建筑类型是否存在
- 位置是否在地图范围内
- 花费是否正确

**Level 3: 状态重放验证（核心）**
- 服务端使用相同规则重放操作
- 计算理论结果并对比实际结果

**Level 4: 统计异常检测**
- 击杀效率异常
- 资源效率异常
- 操作频率异常
- 分数增长曲线异常

关键原则：服务端需要能够独立计算"理论上可能的最大收益"，任何超出范围的提交都是作弊。

---

## 3. 需要服务端执行的关键逻辑

prompt:

对于当下的这个游戏，如果加入排行榜功能，哪些逻辑是需要在服务端执行的？请指出这些重要的逻辑。

answer:

必须服务端控制的逻辑：

| 序号 | 逻辑模块 | 服务端用途 |
|------|----------|------------|
| 1 | 怪物属性表 | 计算每波最大收益 |
| 2 | 波次配置 | 验证怪物数量 |
| 3 | 自动生成算法 | 重放怪物生成 |
| 4 | 建筑属性表 | 验证建造成本 |
| 5 | 升级成本公式 | 验证升级花费 |
| 6 | 出售回收公式 | 验证出售收入 |
| 7 | 难度调整算法 | 验证难度变化 |
| 8 | 波次奖励规则 | 验证生命恢复 |
| 9 | 伤害计算公式 | 验证击杀合理性 |
| 10 | 随机种子逻辑 | 确定性重放 |

核心原则：任何影响 `TD.score` 和 `TD.money` 变化的逻辑都需要服务端可验证。

## 4. 客户端数据提交方案（完整版）

prompt:

如果要验证所有影响 score 和 money 的属性。客户端要在什么时候，提交什么内容。

answer:

提交分为三个阶段：

**阶段 1：游戏开始**
- 时机：玩家点击"开始游戏"
- 请求：`{playerId, clientVersion, timestamp}`
- 响应：`{sessionId, seed, monsterConfig, buildingConfig, waveConfig, initialState}`

**阶段 2：每波结束**
- 时机：当 `map.monsters.length == 0`
- 提交：操作日志、怪物配置、战斗结果、结束状态、建筑列表

**阶段 3：游戏结束**
- 时机：生命归零或玩家退出
- 提交：最终状态、全局统计、所有波次摘要

数据量估算：一局完整游戏（42 波）约 50-60KB 数据量。

---

## 5. 标准模式数据提交方案

prompt:

如果采用标准模式。请再次回答上面的问题。

answer:

标准模式核心思路：记录玩家操作 + 波次摘要，不记录每次击杀细节。

**波次结束时提交**：
```javascript
{
    sessionId: "sess-abc-123",
    waveNumber: 5,
    actions: [
        {type: "BUILD", frame: 2410, building: "cannon", position: [5, 6], cost: 100},
        {type: "UPGRADE", frame: 3100, buildingId: "b-003", cost: 75}
    ],
    monsters: [{type: 0, count: 3}, {type: 1, count: 2}],
    result: {
        killed: 4,
        passed: 1,
        scoreGained: 55,
        moneyGained: 70
    },
    endState: {money: 655, score: 375, life: 94, difficulty: 1.15},
    buildings: [...]
}
```

优势：数据量适中（~50KB/局），验证精度足够，实现复杂度可控。

## 6. 伤害和生命造假的检测

prompt:

如果客户端通过对建筑物的伤害进行造假，或者对怪物的生命进行造假（减少生命）。上面的方案中，对成本和收益的检测，是否可以检测出来？如果要检测出来，是否需要在客户端，引入新的客户端指标？

answer:

**当前方案无法检测这类作弊**。收益没有超限，数量也对得上，但玩家用了"不可能的方式"击杀了怪物。

**需要引入新指标**：
```javascript
result: {
    killed: 4,
    passed: 1,
    scoreGained: 55,
    moneyGained: 70,
    // 新增指标
    totalDamageDealt: 650,           // 总伤害
    totalLifeDestroyed: 520,         // 击杀怪物的总生命值
    waveDurationFrames: 720          // 波次持续帧数
}

buildings: [{
    type: "cannon",
    level: 2,
    damageDealt: 320,                // 本建筑造成伤害
    kills: 3                         // 本建筑击杀数
}]
```

服务端验证流程：
1. 生命池验证：`totalLifeDestroyed == Σ(killed[type] × monsterLife[type])`
2. 伤害验证：`totalDamageDealt ≥ totalLifeDestroyed`
3. DPS 容量验证：`totalDamageDealt ≤ 建筑最大输出 × 时间`
4. 建筑一致性：`Σ(building.damageDealt) ≈ totalDamageDealt`

## 7. 改进方案下仍存在的作弊可能

prompt:

在上一个回答的改进方案下，客户端是否还存在什么作弊的可能性？

answer:

**仍然存在的作弊方式**：

| 作弊方式 | 原方案 | 改进方案 | 加强方案 |
|----------|--------|----------|----------|
| 修改 score/money | ✅ 能检测 | ✅ 能检测 | ✅ 能检测 |
| 增加建筑伤害 | ❌ | ✅ 能检测 | ✅ 能检测 |
| 减少怪物生命 | ❌ | ✅ 能检测 | ✅ 能检测 |
| 移除怪物护甲 | ❌ | ⚠️ 部分 | ✅ 能检测 |
| 增加建筑射程 | ❌ | ❌ | ⚠️ 部分 |
| 移除攻击冷却 | ❌ | ⚠️ 部分 | ✅ 能检测 |
| 减慢怪物速度 | ❌ | ❌ | ⚠️ 部分 |
| 自动瞄准/外挂 | ❌ | ❌ | ⚠️ 部分 |

**无法完全防御的作弊**：
- 自动瞄准（建筑总是命中，但 DPS 没变）
- 完美操作（最优建造时机、最优升级顺序）
- 信息透视（提前知道下一波怪物类型）

这些作弊不改变游戏规则，只是"玩得更好"，无法通过数据验证检测。

## 8. 路径验证机制

prompt:

解释方案 3 中，路径验证是如何生效的？如何避免客户端通过伪造出场的怪物的属性（最高回报、最慢速度），然后通过伪造路径（路线重复，比如绕着建筑物转圈），实现完美游戏？从而实现高分？

answer:

**当前路径验证的局限**：只验证"路径是否存在"，不验证"路径是否合理"。

**核心漏洞**：怪物属性由客户端报告，服务端没有权威数据源。

**根本解决方案：服务端权威**

游戏开始时，服务端返回完整配置：
```javascript
{
    sessionId: "sess-123",
    seed: 987654321,
    monsterConfig: {
        0: {life: 50, speed: 1.0, score: 10, money: 15},
        // ...
    },
    waveConfig: [...],
    buildingConfig: {...}
}
```

验证流程：
1. 服务端定义怪物属性（生命、速度、奖励）
2. 服务端定义每波怪物配置
3. 服务端根据建筑布局计算预期路径长度
4. 验证波次时长是否在合理范围
5. 验证收益不超过服务端计算的最大值

防止"绕圈攻击"：
- 服务端计算预期路径长度
- 验证波次时长：`actualDuration < expectedMax × 2.5`
- 击杀时间分布必须符合路径逻辑

## 9. 客户端与服务端的职责划分

prompt:

在上一个回答的方案下，客户端中，怪物的路线也是服务端下发的么？客户端需要在什么时候，提交什么信息到服务器上？

answer:

**职责划分**：
- 服务端：定义规则 + 验证结果
- 客户端：执行游戏 + 报告结果

**服务端不下发具体路径坐标**，只下发配置。客户端自己计算路径，服务端验证结果是否合理。

**通信时序**：

| 阶段 | 时机 | 客户端提交 | 服务端返回 |
|------|------|------------|------------|
| 开始 | 点击开始 | playerId, version | sessionId, seed, 所有配置 |
| 进行 | 实时 | 无 | 无 |
| 波次结束 | 怪物清空 | buildings, actions, result | valid, serverState |
| 游戏结束 | 生命归零/退出 | finalState, stats, waves | rank, verified |

关键：路径由客户端本地计算，服务端只验证结果是否符合预期范围。

## 10. 实时上传 vs 批量上传

prompt:

客户端是否需要在怪物被击杀时，上传信息给服务端？客户端是否需要在创建、更新、出售建筑物时，上传信息给服务端？

answer:

**不需要实时上传**，采用"本地记录 + 波次结束批量上传"方式。

| 事件 | 是否实时上传 | 处理方式 |
|------|--------------|----------|
| 怪物被击杀 | ❌ 否 | 本地记录，波次结束时上传 |
| 建造建筑 | ❌ 否 | 本地记录，波次结束时上传 |
| 升级建筑 | ❌ 否 | 本地记录，波次结束时上传 |
| 出售建筑 | ❌ 否 | 本地记录，波次结束时上传 |
| **波次结束** | ✅ 是 | 批量上传所有记录 |
| **游戏结束** | ✅ 是 | 上传最终结果 |

**批量上传优势**：
- 请求次数：44 次 vs 585 次（减少 93%）
- 游戏流畅，无网络延迟感
- 服务器负载低
- 支持离线进行

## 11. 时间戳记录需求

prompt:

客户端在怪物被击杀时，是否需要记录时间戳到本地？客户端在创建、更新、出售建筑物时，是否需要记录时间戳到本地？

answer:

| 事件类型 | 是否需要记录时间 | 推荐方式 |
|----------|------------------|----------|
| 建造建筑 | ✅ 需要 | 帧号 (frame) |
| 升级建筑 | ✅ 需要 | 帧号 (frame) |
| 出售建筑 | ✅ 需要 | 帧号 (frame) |
| 击杀怪物 | ⚠️ 可选 | 不记录或仅记录首末时间 |

**建筑操作需要记录帧号的原因**：
- 验证操作顺序（必须先建造才能升级）
- 计算 DPS 贡献时间窗口
- 验证资金流水

**击杀可以不记录的原因**：
- 已有波次时长验证
- 已有 DPS 容量验证
- 已有生命池验证
- 击杀时间可通过其他数据间接验证

使用帧号而非时间戳：帧号是游戏内部时间，避免客户端系统时间被篡改。

---

## 总结：推荐方案

对于此 HTML5 塔防游戏，推荐采用 **Level 1+2+4** 验证方案：

1. **基础验证**：收益上限、成本验证、数量一致性
2. **伤害验证**：生命池验证、DPS 容量验证、攻击次数验证
3. **统计分析**：击杀率异常、资源效率异常、历史对比

实现成本中等，可检测 85% 以上的作弊行为。
